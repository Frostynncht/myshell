# ТЗ семестрового проекта по разработке командного интерпретатора (shell) v0.1

## Описание проекта

Целью проекта является разработка командного интерпретатора (shell) для UNIX/Linux
на языке C.

Командный интерпретатор — программа, которая читает строки команд, разбирает их
и организует выполнение других программ: порождает процессы, настраивает их
стандартные потоки ввода-вывода, связывает процессы каналами и управляет их
выполнением на переднем плане и в фоне.

Необходимо реализовать полный путь обработки команды, включающий лексический
анализ, синтаксический анализ, построение дерева команд и его исполнение
средствами системных вызовов POSIX.

Ожидается работающая учебная реализация, а не код production-уровня.

## Общие положения

### Эталон поведения

Эталоном поведения является **bash**: результат выполнения команды
разрабатываемым интерпретатором сверяется с результатом выполнения той же
команды в bash.

### Границы реализации

Перечень поддерживаемых возможностей задан разделом «База» настоящего документа.
Конструкция, не перечисленная в этом разделе, обрабатывается как ошибка:
выводится диагностическое сообщение, команда не выполняется. Молчаливое
игнорирование неподдерживаемой конструкции и попытка выполнить её частично
не допускаются.

Отклонение от базовых требований допускается только по согласованию
и должно быть явно отражено в отчёте.

### Имя программы

Исполняемый файл интерпретатора называется `mysh` (**TO BE DEFINED** — имя может
быть изменено). Это имя используется в сообщениях об ошибках.

## Требования к shell

### База

Следующие требования являются обязательными для всех студентов.

#### Лексика

Ввод интерпретатора — последовательность строк. Строка разбивается
на **лексемы** (токены) двух видов: слова и операторы.

**Метасимволы** — символы, которые вне кавычек разделяют лексемы:

```
пробел  табуляция  перевод строки  |  &  ;  (  )  <  >
```

**Операторы** — лексемы, состоящие из метасимволов:

```
|  &  ;  &&  ||  (  )  <  >  >>
```

При разборе операторов действует правило максимального совпадения: из двух
возможных вариантов выбирается более длинный (`&&` вместо двух `&`, `>>`
вместо двух `>`).

**Слово** — последовательность символов, ограниченная метасимволами или
кавычками. Слова используются как имя команды, её аргументы и имена файлов
в перенаправлениях.

**Комментарии** — символ `#`, встреченный вне кавычек в начале слова,
делает остаток строки комментарием; комментарий отбрасывается и на выполнение
не влияет.

#### Кавычки

Кавычки позволяют включить метасимволы в состав слова.

**Одинарные кавычки** `'...'` — все символы внутри сохраняют буквальное значение.
Символ `\` внутри одинарных кавычек является обычным символом; включить
одинарную кавычку внутрь такой пары невозможно.

**Двойные кавычки** `"..."` — все символы внутри сохраняют буквальное значение,
кроме `\`. Внутри двойных кавычек `\` экранирует только символы `"`, `\`
и перевод строки; перед любым другим символом `\` остаётся обычным символом
(например, `"a\tb"` выводится как `a\tb`, а не с символом табуляции).

**Обратная косая черта** `\` вне кавычек экранирует следующий за ней символ,
лишая его специального значения. Сочетание `\` и перевода строки означает
продолжение команды на следующей строке; в интерактивном режиме при этом
выводится вторичное приглашение.

Дополнительные правила:

- кавычки не разделяют слово: `a"b c"d` является одним словом `ab cd`;
- пустая пара кавычек образует аргумент нулевой длины, который передаётся
  команде наравне с остальными;
- кавычки удаляются из слова перед передачей аргументов команде;
- незакрытая кавычка в неинтерактивном режиме является синтаксической ошибкой.

#### Синтаксис

Грамматика поддерживаемого подмножества. Конструкции записаны в EBNF,
лексемы — регулярными выражениями:

```
list        = and_or , { ( ";" | "&" ) , [ and_or ] } ;
and_or      = pipeline , { ( "&&" | "||" ) , pipeline } ;
pipeline    = command , { "|" , command } ;
command     = simple | subshell ;
subshell    = "(" , list , ")" , { redirection } ;
simple      = { redirection } , word , { word | redirection } ;
redirection = ( "<" | ">" | ">>" ) , word ;

word        = /([^ \t\n|&;()<>'"\\]|\\.|'[^']*'|"([^"\\]|\\.)*")+/
```

Пояснения:

- простая команда обязана содержать хотя бы одно слово; перенаправления
  могут стоять в любой позиции, в том числе до имени команды
  (`> out echo hi` эквивалентно `echo hi > out`);
- разделитель `&` означает запуск предшествующего элемента списка в фоне,
  разделитель `;` — последовательное выполнение;
- перевод строки завершает разбор списка и эквивалентен `;`.

Синтаксическая ошибка не прерывает работу интерактивного интерпретатора:
выводится диагностическое сообщение, устанавливается код возврата `2`,
после чего ввод продолжается. В неинтерактивном режиме выполнение прекращается
с кодом возврата `2`.

#### Выполнение простой команды

Если имя команды совпадает с именем встроенной команды, выполняется встроенная
команда. Иначе запускается внешняя программа: интерпретатор порождает дочерний
процесс вызовом `fork` и заменяет его образ вызовом из семейства `exec`.

Окружение дочернего процесса совпадает с окружением интерпретатора.

**Коды возврата.** Код возврата команды определяется по результату
системного вызова `waitpid`:

- нормальное завершение — код, возвращённый программой (`WEXITSTATUS`);
- завершение по сигналу с номером `N` — код `128 + N` (`WTERMSIG`);
- команда найдена, но не может быть выполнена (нет прав, это каталог,
  неверный формат файла) — код `126`;
- команда не найдена — код `127`.

Ошибка, обнаруженная в дочернем процессе после `fork`, но до успешной замены
образа процесса, приводит к завершению этого дочернего процесса с кодом `126`
или `127`; возврат в главный цикл интерпретатора из дочернего процесса
недопустим.

Код возврата интерпретатора при завершении равен коду возврата последней
выполненной команды.

#### Перенаправления ввода-вывода

Поддерживаются операторы:

| Запись | Действие |
|--------|----------|
| `< файл` | открыть файл на чтение и связать со стандартным потоком ввода |
| `> файл` | открыть файл на запись, создав его или обрезав до нулевой длины, и связать со стандартным потоком вывода |
| `>> файл` | открыть файл на запись с добавлением в конец и связать со стандартным потоком вывода |

Требования:

- перенаправления применяются слева направо;
- перенаправления применяются после `fork`, но до замены образа процесса,
  то есть затрагивают только выполняемую команду;
- для встроенной команды, выполняемой без конвейера, перенаправления
  применяются в самом процессе интерпретатора: исходные дескрипторы
  сохраняются вызовом `dup`, а после выполнения восстанавливаются;
- ошибка открытия файла отменяет выполнение команды, выводится
  диагностическое сообщение, код возврата — `1`;
- права доступа при создании файла — `0666` с учётом `umask` процесса.

Не входят в базу: перенаправления с явным номером файлового дескриптора
(`2> файл`, `2>&1`, `n>&-`), а также `>|`, `<>`, `<<`, `<<<`, `&>`,
`{fd}>` и пути вида `/dev/tcp/...`.

#### Конвейеры

Конвейер — последовательность команд, разделённых `|`, где стандартный вывод
каждой команды соединён со стандартным вводом следующей через **канал** (pipe).

Требования:

- поддерживается произвольное число команд в конвейере;
- все команды конвейера запускаются одновременно и выполняются параллельно;
- каждый процесс конвейера обязан закрыть все дескрипторы каналов, которые
  он не использует; неиспользуемые открытые концы канала приводят к тому,
  что читающая команда не получает признак конца файла и конвейер зависает;
- встроенная команда в составе конвейера выполняется в дочернем процессе,
  поэтому её побочные эффекты (например, смена каталога) не влияют
  на интерпретатор;
- код возврата конвейера равен коду возврата последней команды;
- конвейер целиком является одним заданием (см. «Управление заданиями»).

#### Списки команд

Поддерживаются операторы:

- `;` — последовательное выполнение;
- `&` — запуск в фоне, интерпретатор не ожидает завершения и сразу
  переходит к следующей команде;
- `&&` — следующий элемент выполняется только при нулевом коде возврата
  предыдущего;
- `||` — следующий элемент выполняется только при ненулевом коде возврата
  предыдущего.

Операторы `&&` и `||` имеют одинаковый приоритет и левую ассоциативность;
оба приоритетнее `;` и `&`.

#### Подоболочки

Подоболочка `( список )` выполняет список команд в отдельном дочернем процессе.

Требования:

- изменения состояния внутри подоболочки не видны интерпретатору
  (например, `cd /tmp` внутри `( )` не меняет текущий каталог);
- подоболочка допускает перенаправления, применяемые ко всему списку:
  `(cmd1; cmd2) > out`;
- подоболочка может входить в конвейер: `(cmd1; cmd2) | cmd3`;
- подоболочки допускают вложенность;
- код возврата подоболочки равен коду возврата последней выполненной
  в ней команды.

#### Встроенные команды

Встроенная команда (builtin) выполняется самим интерпретатором, без запуска
внешней программы. Реализация встроенными обязательна для команд, изменяющих
состояние интерпретатора: во внешней программе такое изменение затронуло бы
только дочерний процесс.

Базовый набор:

| Команда | Назначение |
|---------|-----------|
| `cd [каталог]` | смена текущего каталога |
| `pwd` | вывод текущего каталога |
| `echo [-n] [аргументы]` | вывод аргументов |
| `help` | краткая справка по встроенным командам |
| `exit [код]` | завершение работы интерпретатора |
| `jobs` | список заданий |
| `fg [%n]` | перевод задания на передний план |
| `bg [%n]` | продолжение остановленного задания в фоне |
| `kill` | отправка сигнала процессу или заданию |
| `wait [pid\|%n]` | ожидание завершения заданий |

Команды `jobs`, `fg`, `bg`, `kill`, `wait` описаны в разделе «Управление
заданиями».

**`cd`** — принимает не более одного аргумента. Без аргумента выполняется
переход в каталог из переменной окружения `HOME`, получаемой вызовом `getenv`;
если переменная не установлена, выводится сообщение об ошибке и возвращается
код `1`. Ошибки (каталог не существует, не является каталогом, нет прав)
сопровождаются диагностическим сообщением и кодом возврата `1`.
Раскрытие `~` и переход `cd -` в базу не входят.

**`pwd`** — выводит абсолютный путь текущего каталога, полученный вызовом
`getcwd`. Опции не поддерживаются.

**`echo`** — выводит аргументы через один пробел и завершает вывод переводом
строки. Поддерживается единственная опция `-n`, подавляющая завершающий перевод
строки. Экранированные последовательности (`\n`, `\t` и др.) не
интерпретируются. Команда обязана корректно работать с перенаправлением
(`echo hi > файл`) и в составе конвейера (`echo hi | cat`).

**`help`** — выводит список встроенных команд с кратким описанием. Формат
вывода определяется студентом.

**`exit`** — завершает работу интерпретатора с указанным кодом; без аргумента
используется код возврата последней команды. Код приводится к диапазону
`0..255`. При наличии остановленных заданий первая попытка выхода выводит
предупреждение и не завершает интерпретатор; повторная команда `exit`
завершает его.

#### Управление заданиями

**Задание** (job) — единица работы интерпретатора, порождённая одной командой,
одним конвейером или одной подоболочкой. Задание может состоять из нескольких
процессов.

**Группа процессов** (process group) — набор процессов с общим идентификатором
`pgid`, которому можно послать сигнал целиком. **Группа переднего плана**
терминала — единственная группа, которой разрешено читать с терминала
и получать сигналы от нажатий клавиш.

Требования к инициализации:

- при старте в интерактивном режиме интерпретатор помещает себя в собственную
  группу процессов (`setpgid`) и делает её группой переднего плана
  (`tcsetpgrp`);
- интерпретатор игнорирует сигналы `SIGINT`, `SIGQUIT`, `SIGTSTP`, `SIGTTIN`,
  `SIGTTOU`; игнорирование `SIGTTOU` необходимо, поскольку иначе вызов
  `tcsetpgrp` остановил бы сам интерпретатор;
- дочерние процессы получают обработку сигналов, восстановленную
  в значение по умолчанию, до замены образа процесса.

Требования к запуску задания:

- все процессы одного задания помещаются в одну группу процессов,
  идентификатор которой равен идентификатору первого процесса задания;
- вызов `setpgid` выполняется и в родительском, и в дочернем процессе,
  поскольку порядок их выполнения после `fork` не определён, а к моменту
  первого обращения к группе она обязана существовать;
- задание переднего плана получает терминал вызовом `tcsetpgrp`;
  после завершения или остановки задания интерпретатор возвращает терминал
  себе;
- ожидание задания переднего плана выполняется с флагом `WUNTRACED`,
  чтобы получить уведомление об остановке процесса, а не только
  о его завершении;
- при запуске в фоне выводится строка вида `[1] 12345`, содержащая номер
  задания и идентификатор процесса.

Требования к состояниям и уведомлениям:

- задание находится в одном из состояний: выполняется (`Running`),
  остановлено (`Stopped`), завершено (`Done`);
- нажатие Ctrl-C посылает `SIGINT`, Ctrl-Z — `SIGTSTP` группе переднего
  плана, а не интерпретатору; при отсутствии задания переднего плана
  интерпретатор продолжает работу и выводит новое приглашение;
- уведомления об изменении состояния фоновых заданий выводятся перед
  очередным приглашением, а не в произвольный момент;
- завершившиеся процессы не должны оставаться в состоянии «зомби»:
  для каждого порождённого процесса обязан быть выполнен `waitpid`;
- номера завершённых заданий переиспользуются.

**`jobs`** — выводит список заданий. Формат строки:

```
[1]+  Running                 sleep 10 &
[2]-  Stopped                 cat
```

Маркер `+` обозначает текущее задание (последнее переведённое в фон или
остановленное), маркер `-` — предыдущее.

**`fg [%n]`** — переводит задание на передний план: посылает группе `SIGCONT`,
передаёт ей терминал и ожидает завершения или остановки. Без аргумента
используется текущее задание. Перед ожиданием выводится командная строка
задания.

**`bg [%n]`** — продолжает выполнение остановленного задания в фоне: посылает
группе `SIGCONT`, не передавая терминал.

**`kill`** — посылает сигнал. Поддерживаемые формы:

```
kill [-s СИГНАЛ | -СИГНАЛ] цель ...
```

Сигнал задаётся номером или именем (`TERM`, `SIGTERM`, `9`); по умолчанию —
`SIGTERM`. Цель — идентификатор процесса либо спецификатор задания.

**`wait [pid|%n]`** — без аргументов ожидает завершения всех фоновых заданий
и возвращает `0`; с аргументом ожидает указанное задание и возвращает
его код возврата.

**Спецификаторы заданий**: `%n` — задание с номером `n`, `%+` — текущее
задание, `%-` — предыдущее. Спецификаторы по имени команды (`%имя`, `%?текст`)
в базу не входят.

#### Режимы запуска

```
mysh                     # интерактивный режим
mysh -c 'команда'        # выполнение одной строки
mysh < файл              # чтение команд из стандартного потока ввода
```

**Интерактивный режим** — стандартный ввод связан с терминалом. Выводится
приглашение, включено управление заданиями, ошибки не прерывают работу.
Формат приглашения определяется студентом. При получении признака конца файла
(Ctrl-D) интерпретатор завершает работу.

**Неинтерактивный режим** — ввод получен из файла, канала или через `-c`.
Приглашение не выводится, управление заданиями отключено: команды `fg` и `bg`
завершаются с ошибкой, терминал не передаётся. Запуск в фоне (`&`)
и команда `wait` работают. Такое поведение повторяет bash и делает возможной
автоматическую проверку.

Запуск файла-скрипта как аргумента командной строки в базу не входит.

Дополнительно поддерживаются отладочные режимы:

- `--dump-tokens` — вывести поток лексем и завершить работу;
- `--dump-ast` — вывести дерево команд в читаемом виде и завершить работу.

#### Возможности, не входящие в базу

## Требования к архитектуре

Интерпретатор должен быть реализован в виде последовательного прохода
из независимых фаз. Каждая фаза принимает на вход результат предыдущей
и не зависит от деталей её реализации.

```
Строка ввода
     ↓
  [Лексер]        → поток лексем
     ↓
  [Парсер]        → дерево команд (AST)
     ↓
 [Исполнитель]    → системные вызовы: fork, exec, pipe, dup2, waitpid
     ↓
 Код возврата
```

Требования:

- каждая фаза реализуется отдельным модулем (парой `.c`/`.h`);
- смешивание фаз не допускается: исполнитель не работает с исходным текстом
  команды, лексер и парсер не выполняют системных вызовов;
- разбор выполняется методом рекурсивного спуска: грамматика содержит
  вложенные конструкции (подоболочки), поэтому разбиение строки
  на части по разделителям недостаточно;
- дерево команд обязано быть явной структурой данных, а не последовательностью
  действий, выполняемых по ходу разбора;
- управление заданиями выделяется в отдельный модуль, инкапсулирующий
  таблицу заданий.

Конкретный набор модулей определяется студентом. Рекомендуемое разбиение:
лексер, парсер, исполнитель, перенаправления, встроенные команды,
задания, сигналы.

## Требования к коду на C

### Стиль и качество кода

- код должен быть единообразно оформлен на протяжении всего проекта;
- каждый модуль должен иметь краткий комментарий с описанием назначения;
- использование «магических чисел» и необъяснимых конструкций
  без комментариев не допускается;
- глобальное состояние допускается только для таблицы заданий
  и данных, изменяемых из обработчика сигнала; оно должно быть
  ограничено одним модулем.

### Ограничения

Запрещено:

- `system`, `popen` — выполняют команду средствами внешнего shell;
- `wordexp` — выполняет разбор и раскрытие слов;
- `glob`, `fnmatch` — раскрытие имён по шаблону в базу не входит;
- `readline`, `libedit` и другие библиотеки редактирования строки;
- генераторы лексеров и парсеров (`flex`, `bison`, `re2c` и аналоги);
- сторонние библиотеки, не согласованные с преподавателем.

Разрешено:

- стандартная библиотека C и интерфейсы POSIX.

### Обработка ошибок

- результат каждого системного вызова обязан проверяться;
- системные вызовы, прерываемые сигналом, обязаны корректно обрабатывать
  ошибку `EINTR`: вызов повторяется либо ситуация обрабатывается явно.
  Это требование существенно для `waitpid`, `read` и `write`
  в интерактивном режиме, где сигналы приходят регулярно;
- ошибка системного вызова и ненулевой код возврата команды — разные
  ситуации, и они не должны смешиваться;
- диагностические сообщения выводятся в `stderr` в едином формате:

```
mysh: <команда>: <сообщение>
```

  где `<сообщение>` для ошибок системных вызовов формируется на основе
  `strerror(errno)`;

- обработчик сигнала обязан использовать только функции, безопасные для вызова
  из обработчика (async-signal-safe); значение `errno` внутри обработчика
  сохраняется и восстанавливается.

### Требования к ресурсам

- отсутствие процессов-зомби: для каждого порождённого процесса
  выполняется `waitpid`;
- отсутствие утечек файловых дескрипторов: число открытых дескрипторов
  интерпретатора не растёт с числом выполненных команд;
- отсутствие утечек памяти и ошибок доступа к памяти. Проверяется двумя
  способами: сборкой с `-fsanitize=address,undefined` и запуском
  под `valgrind --leak-check=full --track-fds=yes`. Оба запуска обязаны
  завершаться без сообщений об ошибках и без потерянных блоков памяти.
